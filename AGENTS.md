# AGENTS.md

Context for AI agents working on **Viral**. Read this before changing
anything. The section on rendering surfaces is the one that prevents
silent, user-visible breakage.

---

## What this is

Viral is an internal Shifu Labs tool for a small invite-only group of
LinkedIn posters. It turns HTML — usually generated by Claude from a
skill — into finished LinkedIn images, and keeps the performance numbers
those posts earn so the next post can start from what worked.

Three output formats, one flow each:

| Mode | Input | Output |
|---|---|---|
| Infographic | one HTML file, pasted | 1080×1350 PNG |
| Carousel | a .zip of 1080×1080 slide HTMLs | multi-page PDF |
| Tweet | a form (persona, body, engagement counts) | 1080×1350 PNG |

Around that: a per-user logo library that compounds, brand themes, a
post wall with manually-tracked impressions, a member directory, and a
docs section holding the team's skills and tool catalog.

## Stack

- **Next.js 14.2.35**, App Router, React 18, TypeScript strict
- **Tailwind CSS v3** (`tailwind.config.ts` + `@tailwind` directives).
  Not v4 — do not use `@theme` or v4-only utilities like `shadow-xs`,
  `outline-hidden`, or `field-sizing-content`. They compile to nothing.
- **Prisma** + Postgres · **BullMQ** + Redis · **Auth.js (NextAuth v5)**
- **S3-compatible storage** (Cloudflare R2 in production)
- Rendering: `html-to-image` in the browser, `puppeteer-core` in a
  separate worker service for carousel PDFs
- shadcn-style primitives in `components/ui/`, hand-vendored — there is
  no `components.json`, so no CLI will manage them
- Only two Radix packages are actually imported: `react-slot` and
  `react-popover`. `react-dialog`, `react-dropdown-menu` and
  `react-label` are installed but unused.

```
npm run dev         # Next dev server
npm run build       # prisma generate && next build
npm run typecheck   # tsc --noEmit
npm test            # vitest
npm run worker      # render worker (needs Redis)
```

There is **no ESLint config** in the repo — `npm run lint` drops into
Next's interactive setup wizard. Don't run it in an automated context.

## The three rendering surfaces — read this before touching styles

This is the highest-risk thing in the codebase. There are three
surfaces, they have different rules, and confusing them ships broken
images to users.

### 1. App chrome

Everything under `app/` and `components/` that is not listed below.
Styled with Tailwind against the tokens in `styles/globals.css`. Change
freely.

### 2. Generated slides and carousels — **never restyle**

User HTML renders inside an `<iframe srcDoc>` (`components/slide-preview.tsx`)
or Puppeteer's `page.setContent()` (`lib/carousel-exporter.ts`). These
are separate documents; the app's stylesheet never reaches them. The
brand rules do not apply, and "cleaning up" colors here would recolor
posts users already made.

Off-limits for style sweeps:

```
components/slide-preview.tsx      (the iframe + capture)
components/themes/sample-slide.tsx
lib/themes.ts  lib/theme-charts.ts  lib/accent-rewrite.ts
lib/carousel-exporter.ts  workers/
```

### 3. `components/tweet-preview.tsx` — **the trap**

This one is a live React node **in the app's own document**, and it is
also the `html-to-image` capture target (`components/tweet-flow.tsx:494`).
html-to-image inlines computed styles, so anything this component takes
from the Tailwind theme is baked into the user's exported PNG.

Its geometry is therefore **pinned with inline styles on purpose**:
24px card radius, 8px affiliation logo, 9999px/16px avatar, and the
card shadow. Do not "tidy" those back into Tailwind classes.

Why it matters: a previous change emptied `borderRadius` at the theme
level. It compiled clean, exited 0, left CI green — and turned every
exported avatar from a circle into a hard square. No test caught it,
because nothing covers the render path. If you change theme-level radius
or shadow scales, verify the export geometry before and after.

## Design system

Four brand inks, defined once as HSL triplets in `styles/globals.css`
and surfaced as Tailwind colors in `tailwind.config.ts`:

| Ink | Hex | Role |
|---|---|---|
| Off-Black | `#101010` | ground |
| Chalk | `#F1EFEA` | text, primary fills |
| Concrete | `#55534E` | hairlines, secondary text |
| Signal | `#FF4D00` | accent only |

Two deliberate derivations, both documented in `globals.css`:

- `--card` and `--muted` are **Off-Black lifted** along the same warm
  axis. Four inks give one ground, and this UI reads depth from three
  stacked surfaces.
- `--muted-foreground` is **Concrete lightened**. Concrete itself
  measures ~2.5:1 on Off-Black and fails WCAG AA for body text.

Rules:

- **Signal is accent only.** Focus rings, destructive, warning, the
  active-nav rail, one CTA per view. Never a large region fill, never
  body copy.
- Every color in app chrome should resolve to one of the four. Stock
  Tailwind palette classes (`bg-amber-500`, `text-indigo-400`) do not
  belong in chrome — they were all swept out.
- Radii come from `--radius: 0.625rem`. `rounded-xl` is redefined to
  14px, not Tailwind's 12px.
- The shadow ladder is re-weighted for a dark canvas; stock Tailwind's
  5% black is ~0 contrast on `#101010`.
- Motion tokens live in `lib/motion.ts`. 200ms is the workhorse, 500ms
  the ceiling. Surfaces lift 2px on hover and step their shadow up one
  rung; controls press to `scale(0.97)`.

The app is **dark-only**: `.dark` is hard-coded on `<html>`, and
`:root` and `.dark` carry identical values. There is no light palette —
one would have to be authored from scratch.

## Things that look renameable but are not

- **`data-viral-theme` / `data-viral-thumb`** — matched by string across
  `lib/themes.ts`, `components/slide-preview.tsx`,
  `components/themes/sample-slide.tsx` and
  `components/carousel/slide-rail.tsx`. Renaming one without the others
  silently breaks theme injection.
- **localStorage keys** — `viral.activeThemeId`,
  `viral.tweet.styles.v3`, `viral.tweet.carryover.v1`. Renaming these
  silently discards users' saved state.
- Database table names, env var keys, API route paths, package
  directory names. Churn with breakage risk and no user-visible payoff.

The product name is **Viral** (capitalized) in user-visible strings and
metadata only. There is no shared brand constant — the wordmark is
hardcoded in several places.

## Configuration: env vars vs database

Only three secrets are required to boot:

```
DATABASE_URL
REDIS_URL
AUTH_SECRET
```

**Storage, SMTP and Google OAuth live in the `settings` table**, managed
from `/admin`, not in env vars. Consequences worth knowing:

- The invite email's "From" name is a **database row**
  (`lib/email.ts` → `getSettings()` → `email.from`). No code edit
  changes what recipients see; an admin has to update it in
  `/admin/config#email`.
- Without Redis the app still runs, but queued renders never complete
  and `/admin/health` says so. Without S3 credentials, export is
  disabled and the app says so.

Optional env: `NEXT_PUBLIC_SITE_URL` / `NEXTAUTH_URL` (absolute URLs for
og:image), `RENDER_CONCURRENCY`, `PUPPETEER_EXECUTABLE_PATH`.

## Data model and access

Fourteen Prisma models. The ones that carry the product:

- **`Entity`** — the per-user logo library. `UNIQUE(user_id, slug)`, so
  two users can each have a `tesla` and stay independent.
- **`Render`** — one row per exported post. Also holds the manual
  tracking fields (`postUrl`, `publishedAt`, `trackedAt`, `impressions`,
  `reactions`, `comments`, `reposts`) and `sourceHtml` for Remix.
- **`Theme`**, **`Skill`**, **`Tool`**, **`DocPage`** — user- and
  admin-authored content.

**Every Prisma query filters by `user_id`.** Preserve that.

Access is invite-only. First run creates the admin at `/setup`, which
then locks itself. After that: admin-issued invites or approved requests
at `/welcome/request`. There is no public sign-up.

`publishedAt` and `trackedAt` gate the community feed (a post needs to
be 7+ days past publication with metrics logged), the wins leaderboard,
and member stats. If tracking data decays, those pages go quiet.

`requireUser` / `requireAdmin`. There is no middleware.

## Known gaps

Worth knowing before you trust the safety net:

- **Test coverage is two files** — `tests/parser.test.ts` and
  `tests/storage-keys.test.ts`. Entity resolution, carousel export and
  the render pipeline have none. A green test run says very little
  about rendering.
- **No `error.tsx`, `not-found.tsx`, or `global-error.tsx`.** Any
  unmatched URL renders Next's stock **white** 404 on a dark-only
  product. Reachable in normal flow: `app/invite/[token]/page.tsx` calls
  `notFound()` on a malformed invite.
- **No `robots.ts` / `sitemap.ts`** on an invite-only product.
- **No error tracking.** A failed render in the worker just fails.
- `components/tweet-flow.tsx` (~1600 lines) and
  `components/posts-list.tsx` are past the size where changes are safe.
- A theme-seeding migration guards on
  `WHERE user_id IS NULL AND name = 'Default — Dark'`. If a workspace
  renamed the official theme, the later refresh matched zero rows. Any
  fix needs a **new** migration, not an edit to an applied one.
- `next/font/google` fetches Instrument Sans and JetBrains Mono at build
  time, so the build host needs outbound access to `fonts.googleapis.com`.

## Conventions

- Comments explain **why**, not what. Match the surrounding density —
  this codebase comments decisions and non-obvious constraints, and
  skips narrating obvious code.
- Path alias is `@/*` → repo root.
- `cn()` from `lib/utils.ts` (clsx + tailwind-merge) for class
  composition.
- Verify visually when changing rendering. Screenshots beat reasoning
  about CSS — several bugs in this codebase's history compiled cleanly
  and only showed up on screen.
